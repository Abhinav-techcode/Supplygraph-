# Phase 10 — Governed Closed-Loop Execution: Architecture and Implementation

Observe → Understand → Predict → Recommend → Approve (Phases 1–8) → **Execute → Verify → Reconcile → Learn** (this phase). Human approval and deterministic policy remain authoritative at every step.

## 1. Packages
Domain `domain.model.execution`: `ExecutionWorkflow`, `ExecutionTask`, `TaskGraph`, `TaskType`, `TaskStatus`, `WorkflowStatus`, `WorkflowApproval`, `ExecutionPolicy`, `ExecutionAttempt`, `ExecutionEvidence`, `ExecutionEvent`, `ActualMeasurement`, `PlanOutcomeComparison`, `ReassessmentRequest`, `ReassessmentGovernor`, `SeparationOfDutiesException`.
Application `application.execution`: `RecoveryPlanConversionService`, `WorkflowPlanner`, `ExecutionApprovalService`, `ExecutionOrchestrationService`, `ExecutionAcknowledgementService`, `ExecutionReconciliationService`, `ExecutionCompensationService`, `ClosedLoopService`, `ExecutionQueryService`, `ExecutionAdvisoryService`, `AdapterSelector`, `TwinFeedback`, `ExecutionSupport`; port `ExecutionAdapter`.
Adapter: `SandboxExecutionAdapter` (SIMULATED). Persistence: `V11__phase10_execution.sql`, `PostgresExecutionPersistenceAdapter` (JDBC). Web: 12 views under `views.execution`, `ExecutionRecoveryRunner`.
Existing code touched: `RecoveryPlanningApplicationService` gained read-only `revalidateConflicts` (the intent-building code was extracted into a private method shared with the unchanged `validatePlanWithConcurGuard`).

## 2. State machines (domain, not UI)
Workflow: `DRAFT → VALIDATED → PENDING_APPROVAL → APPROVED → READY → EXECUTING → {COMPLETED | PARTIALLY_COMPLETED | FAILED | RECONCILIATION_REQUIRED | COMPENSATION_REQUIRED}`, plus `REJECTED`, `BLOCKED`, `CANCELLED`. Task: `PENDING → READY → IN_PROGRESS → {AWAITING_ACK | COMPLETED | RETRY_PENDING | FAILED | RECONCILIATION_REQUIRED}`, `BLOCKED`, `SKIPPED`, `CANCELLED`, `COMPLETED → COMPENSATED`. Invalid transitions throw; `ExecutionWorkflow.settle()` derives the workflow status from task states.

## 3. Plan → workflow conversion (`RecoveryPlanConversionService.convert`)
1. Plan must be `APPROVED` with an `APPROVED` approval record. 2. Approver must resolve (by id or username) to an **active** user holding `PLAN_APPROVE` with access to the plan's workspace — otherwise the workflow is BLOCKED ("not traceable to a known user"). 3. The twin's current version must equal the plan's source version. 4. Approval older than 7 days → stale. 5. `ConcurGuard` is re-run read-only against the current twin. 6. Tasks and dependencies are generated by the pure `WorkflowPlanner`. 7. Graph validated (cycle detection, Kahn). 8. Persisted with a timeline event and audit entry. Any failure creates a **BLOCKED** workflow (auditable, never executable) and one bounded, deduplicated reassessment proposal. Only one active workflow per plan.
Task chains: `PURCHASE_ORDER_EXPEDITE` → capacity confirmation → expedite PO (sensitive); `ALTERNATIVE_SUPPLIER` → quotation → capacity confirmation; inventory/production tasks wait for procurement chains of the same material; a final `NOTIFY_STAKEHOLDERS` depends on everything. Task types without a plan-action source (`TRIGGER_QUALITY_INSPECTION`, `INITIATE_APPROVED_MATERIAL_SUBSTITUTION`) exist in `TaskType` but the current planner never generates them; conditional tasks are supported by the graph (`withCondition`) but not generated by the planner.

## 4. Governance
* `EXECUTION_CREATE` to convert; `EXECUTION_APPROVE` to approve/reject; `EXECUTION_APPROVE_SENSITIVE` for the second approval; `EXECUTION_RUN` to start/retry/cancel; `EXECUTION_RECONCILE`; `EXECUTION_COMPENSATE`. All enforced in services, against the workflow's own workspace.
* `ExecutionPolicy` per workspace (defaults are the strict ones): approver ≠ creator, executor ≠ approver, sensitive tasks need a *different* second approver, `allowLiveExecution=false`, max attempts 3, max replan depth 2, deviation threshold 15 %. Editable only by `WORKSPACE_ADMIN`.
* A workflow is READY only after the required approvals; `start` re-checks twin staleness and blocks instead of executing an obsolete plan.

## 5. Execution engine
Dependency-aware passes (max 50) compute skippable, blockable and runnable tasks via `TaskGraph`; independent tasks of a pass run one after another (deterministic), not on parallel threads. Per task: persist `IN_PROGRESS` + `STARTED` attempt → call the adapter on a bounded pool (2–4 threads, queue 16, timeout enforced) → persist the outcome. Outcome mapping: ACK → `AWAITING_ACK` (does **not** release dependents); confirmed → `COMPLETED`; retryable → `RETRY_PENDING` (explicit, bounded, same idempotency key); permanent/rejected/auth → `FAILED` and downstream `BLOCKED`; timeout, adapter exception, or crash → `RECONCILIATION_REQUIRED`, which is **never** retried automatically. `ExecutionRecoveryRunner` converts tasks left `IN_PROGRESS` after a crash into `RECONCILIATION_REQUIRED` at startup; nothing is re-sent. Per-workflow in-process locks serialize mutation (single-instance assumption); the repository additionally rejects stale writes by version.

## 6. Evidence, acknowledgements, reconciliation, twin
Evidence kinds: adapter acknowledgement/confirmation, external acknowledgement, observed state, manual confirmation, manual "not executed". Acknowledgements are idempotent (`taskId + reference + outcome`); late acknowledgements are recorded without illegal transitions. Observations compare expected vs observed (numeric-tolerant); mismatch demands reconciliation. **Digital twin feedback (`TwinFeedback`) fires only for non-simulated workflows with validated evidence** and goes through `OperationalEventIngestionService` (`RECOVERY_ACTION_COMPLETED`), i.e. the Phase 5 monitoring pipeline. SIMULATED evidence is stored and labelled but never reaches the twin.

## 7. Compensation
Only completed tasks of types with a real business compensation (`TaskType.compensable()`) can be compensated; irreversible types (reroute/transport mode change, substitution, notification) are refused with an explanation. Operators can alternatively accept the partial result.

## 8. Closed loop
Expected metrics come from the approved plan's `PlanComparisonMetrics`. Actuals are recorded with a source; missing → `UNKNOWN`; recorded for a SIMULATED workflow → `SIMULATED` (never counts). `ReassessmentGovernor` proposes at most one open reassessment, only for real deviations ≥ threshold, and only below the depth limit; otherwise it records suppression or "limit reached — escalate". A human with `PLAN_APPROVE` decides; approval is recorded and handed to the existing Recovery Decision Centre — **no plan is regenerated or executed automatically**. Real measurements are also fed to the monitoring pipeline.

## 9. Agents
`ExecutionAdvisoryService` returns deterministic, read-only explanations tagged with the existing `AgentRole` (e.g. failure explanation, dependency summary, deviation explanation) with `actionable=false`. It holds no mutating dependency (ArchUnit-enforced) and `adapter.ai` cannot depend on execution packages. **No language model is invoked** and the eight agents are not called from execution; this is the boundary they would use. A reassessment proposal goes through the governor and a human decision.

## 10. Views
`/execution-centre`, `/execution-designer`, `/execution-approvals`, `/task-dependencies` (server-rendered SVG graph), `/execution-monitor` (5 s poll), `/execution-failures`, `/execution-acknowledgements`, `/execution-reconciliation`, `/execution-compensation`, `/execution-timeline`, `/plan-vs-actual`, `/closed-loop`. SIMULATED vs LIVE is shown on workflows, attempts, evidence and timeline.

## 11. Not implemented
LIVE execution adapters (including an ERP command adapter); an HTTP endpoint for inbound execution acknowledgements (they are entered through the UI/service); planner-generated conditional tasks and quality-inspection/substitution tasks; automatic plan regeneration; parallel task threads.
